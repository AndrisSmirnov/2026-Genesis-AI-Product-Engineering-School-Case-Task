## D1. Мова коду й спосіб запуску
- **Статус:** decided
- **Рішення:** Go. Запуск через `go -C <skill>/scripts run ./cmd/wikitrend <команда>`. Бінарників у репо немає: `go run` компілює в кеш збірки поза навичкою.
- **Чому:** Go — моя основна мова, тож кожен рядок коду я можу пояснити без AI. `go.mod` і `go.sum` дають відтворювані залежності.
- **Відкинуті альтернативи:**
  - Python + uv має готові `scipy` і `pymannkendall`, але це моя друга мова.
  - Самописна статистика — не мінус: я звірю її з еталонами `scipy`, і це доказ, що я розумію методику.
  - Гібрид подвоює код і тести.
- **Обмеження:** у користувача має бути встановлений Go. `doctor` перевіряє це й дає помилку `GO_MISSING`, а `doctor --warmup` робить першу компіляцію заздалегідь.
- **Версія:** розробка й CI на Go 1.27.1 (остання стабільна, еталон). Рядок `go` у `go.mod` — мінімальна версія, з якою збирається код, визначена заміром (Q1). Без `toolchain`.
- **Як перевірю:** чистий Docker-контейнер, перший `go run` без кешу; заміряю час і перевірю збірку з `GOTOOLCHAIN=local` на образах `golang:1.24`…`1.27`.

## D2. Інтерфейс для агента
- **Статус:** decided
- **Рішення:** 5 високорівневих команд CLI:

  | Команда | Що робить |
  |---|---|
  | `doctor [--warmup]` | Перевіряє Go, мережу до wikimedia.org і wikidata.org, папку кешу |
  | `resolve --topic "…" --langs uk,pl` | Знаходить статті, пише чернетку `runs/<id>/spec.json` |
  | `analyze --spec … \| --from <id> --set k=v` | Завантажує дані, рахує, пише `result.json` |
  | `report --run <id> --narrative <file>` | Графік + PDF на 1 сторінку |
  | `explain --run <id> --lang uk` | Детальні причини рівня довіри, без сирих рядів |

  Правила виходу:
  - stdout — один JSON до 2 КБ: `status`, `summary`, `warnings`, `next_step`, `files`;
  - сирі ряди пишуться лише у `runs/<id>/data.json`;
  - помилка — JSON з `code`, `hint`, `next_step` і ненульовий exit code.
- **Чому:** слабка модель надійно проходить короткий «золотий шлях» з 4–5 кроків. Вона губиться, коли треба самій складати конвеєр із дрібних кроків або читати сотні чисел. `next_step` у кожному виході означає, що моделі не треба пам'ятати процес: вона просто виконує підказку.
- **Відкинуті альтернативи:**
  - 10–15 дрібних команд — більше рішень у моделі, більше місць, де вона помилиться.
  - Окремі `fetch` і `compute` — зайвий крок; що саме впало, і так видно з `code` помилки.
  - MCP-сервер — не формат Agent Skills, якого вимагає завдання; потребує налаштування клієнта. Можливо в roadmap.
- **Як пояснити на захисті:** «CLI — це інтерфейс для моделі. Я мінімізую кількість рішень, які приймає модель, і обсяг даних у її контексті: код рахує, модель керує. Кожна відповідь каже, що робити далі, тому навіть Haiku не губиться.»
- **Як перевірю:** евали на Haiku. Рахую виклики інструментів і помилки на сценарій. Окремо перевіряю: модель жодного разу не написала код сама і не прочитала `data.json`.

## D3. Тема → статті
- **Статус:** decided
- **Рішення:**
  1. `resolve` шукає тему у Wikidata (`wbsearchentities`) і повертає до 5 кандидатів з описами.
  2. Якщо кандидат не один, агент **обов'язково питає користувача**, наприклад «Меркурій — планета чи елемент?».
  3. За обраним QID беремо sitelinks, тобто назви статей у потрібних мовах (`wbgetentities`).
  4. Для кожної статті беремо редиректи (MediaWiki `prop=redirects`) і **сумуємо** їхні перегляди до основної статті. Ліміт — до 30 редиректів на статтю; якщо спрацював ліміт, додається попередження.
  5. Якщо статті в якійсь мові немає, `resolve` не падає, а пише `missing: ["cs"]` і пояснення. Це теж інсайт: у цій мові ніша не заповнена.
  6. Для широких тем («вивчення англійської») використовується **кошик** до 5 QID. Модель пропонує його, користувач підтверджує. Кошик записується в `spec.json` разом з датою.
- **Чому:** QID однозначно ідентифікує тему незалежно від мови: «Астрономія», «Astronomia» й «Astronomie» — один об'єкт. Редиректи API не додає до цільової статті, без них ми недорахуємо перегляди.
- **Відкинуті альтернативи:**
  - Пошук за назвою — у кожній мові назви різні, і там повно омонімів.
  - Категорії — глибина й структура різні між мовами, результати непорівнювані.
- **Як пояснити на захисті:** «Тема — це не рядок, а сутність Wikidata. Через неї я гарантую, що в польській і чеській Wikipedia порівнюю одне й те саме. Неоднозначність не вгадую, а питаю. Список статей фіксую в спеці, щоб аналіз був відтворюваним.»
- **Як перевірю:** живі запити до Wikidata для 5 тем, зокрема неоднозначної «Меркурій» і такої, де статті немає в одній мові. Порівняю з інструментом Langviews на pageviews.wmcloud.org.

## D4. Метрика інтересу
- **Статус:** decided
- **Рішення:**
  - Основна метрика — **місячна частка**: перегляди теми ÷ усі перегляди мовного розділу. І чисельник, і знаменник беремо з `agent=user` (лише люди) та `access=all-access` (усі платформи).
  - **Зростання:**
    - YoY — сума частки за останні 12 міс. ÷ сума за попередні 12 міс. − 1;
    - темп за рік — робастний нахил Theil–Sen по log(частки), переведений у «% за рік».
  - Абсолютні перегляди показуються лише довідково, для розуміння масштабу.
  - Вікно за замовчуванням — **36** повних місяців (було 24; змінено за калібруванням, див. D5 і `VERIFICATION.md` §3). Поточний неповний місяць відкидається.
  - 404 від API означає «нуль переглядів», а не помилку.
- **Чому:**
  - Трафік Wikipedia загалом падає приблизно на 8% за рік (AI-відповіді в пошуку, перекласифікація ботів 2025). В абсолютних числах тема «падала б», навіть якби інтерес до неї ріс. Частка прибирає цей загальний фон.
  - Розділи мають різний розмір, а частку можна порівнювати між мовами.
  - `agent=user` відсікає ботів.
  - Theil–Sen стійкий до поодиноких сплесків, на відміну від звичайної лінійної регресії.
- **Відкинуті альтернативи:**
  - Абсолютні перегляди — маскують тренд.
  - `all-agents` — боти.
  - Порівняння двох точок (місяць до місяця) — один сплеск визначає результат.
  - CAGR з кінцевих точок — теж чутливий до сплесків.
- **Як пояснити на захисті:** «Я міряю не скільки людей читали статтю, а яку частку уваги читачів розділу вона забирає. Так я відділяю інтерес до теми від того, що Wikipedia загалом втрачає трафік, і можу чесно порівнювати велику польську Wikipedia з меншою чеською.»
- **Як перевірю:** синтетичні ряди з відомою відповіддю (+20% за рік на фоні падіння знаменника −8%) — код має показати ≈ +20%. Ручна звірка 3 кейсів з pageviews.wmcloud.org.

## D5. Рівень довіри
- **Статус:** decided (пороги — гіпотези до калібрування)
- **Рішення:** три рівні — **високий / середній / низький** — і завжди список причин. Рівень визначають 7 перевірок:

  | # | Перевірка | Що питає |
  |---|---|---|
  | C1 | Напрям | Чи є статистично стабільний тренд (сезонний Mann–Kendall)? |
  | C2 | Величина | Чи зростання практично помітне (≥ +10% за рік)? |
  | C3 | Сплески | Чи тренд лишається після видалення сплесків (новини, Doodle)? |
  | C4 | Обсяг | Чи достатньо переглядів (≥1000/міс; <300 — одразу «низький»)? |
  | C5 | Чутливість | Чи висновок той самий на вікнах 24/36 міс.? |
  | C6 | Злам 2025 | Чи зростання не зосереджене на періоді перекласифікації ботів? |
  | C7 | Кошик | Чи більшість статей кошика ростуть в один бік? |

  - **Високий:** пройдено C1–C5, а також C6 або C7.
  - **Середній:** C1 пройдено, але провалено одну з C2, C3, C5 або C6.
  - **Низький:** провалено C1 або C4.
- **Чому:** фаундеру потрібна відповідь «можна на це спиратися чи ні», а не p-value. Одне p-value обманює: сезонність, автокореляція, сплески. Кілька незалежних перевірок з причинами дають зрозумілий і чесний висновок.
- **Відкинуті альтернативи:**
  - p-value — незрозуміле й оманливе.
  - Числовий бал 0–100 — хибна точність.
- **Як пояснити на захисті:** «Довіра — це не одна статистика, а відповідь на питання "що могло б зробити цей висновок хибним?": шум, сплеск, малий обсяг, вибір періоду, зміна обліку ботів. Кожне таке питання — окрема перевірка. Пороги я не вигадав, а відкалібрував на синтетичних рядах із відомою відповіддю.»
- **Як перевірю:** по 500 синтетичних рядів на кожен клас (+5/+15/+30% за рік, пласкі зі сплесками, ступінчасті). Цілі: на пласких рядах «високий» ≤5% випадків, на +15% за рік «високий» ≥70%.
- **Зміни під час реалізації (verified):**
  - **Інтервал:** замість block bootstrap — інтервал Сена (1968) з поправкою на автокореляцію. Бутстреп у симуляції накривав справжній нахил лише у 78% випадків замість 90%.
  - **Калібрування** (`calibrate_test.go`, 200 рядів на клас):
    - 36 міс.: «високий» — 0% на пласких рядах і 82% на +15% за рік → цілі виконано;
    - 24 міс.: 36% на +15% за рік → вікно за замовчуванням змінено на 36 міс., для коротших вікон додано попередження `short_window`.
  - **C3 і C6:** «схожий тренд» = різниця < max(50%, 5 п.п.), бо біля нуля відносне правило ламалось.

## D6. Повторні запити: спека й кеш
- **Статус:** decided
- **Рішення:**
  - **Спека.** Кожен аналіз описується файлом `spec.json`: QID, статті, мови, період, параметри. `run_id` — хеш спеки: та сама спека дає той самий результат і той самий `run_id`.
  - **Уточнення.** «А за 3 роки?» виконується так: `analyze --from <run_id> --set window.months=36`. Створюється нова спека з посиланням на батьківську (`parent_run_id`), `resolve` повторно не запускається.
  - **Кеш.** Відповіді API зберігаються файлами `cache/<sha256(url)>.json`. Завершені місяці не змінюються, тому кешуються назавжди. Поточний місяць живе 24 години.
- **Чому:** уточнення — це зміна одного параметра, а не новий аналіз з нуля. Повторний запит бере дані з кешу: швидко, без лімітів API, ті самі числа.
- **Відкинуті альтернативи:**
  - YAML — ще одна залежність без користі для моделі.
  - SQLite / bbolt — для v1 зайве; файли простіші, їх легко подивитися й видалити. SQLite (`modernc.org/sqlite`) — у v2, коли даних стане багато.
- **Як пояснити на захисті:** «Аналіз — це функція від спеки. Уточнення користувача перетворюється на зміну одного поля, а кеш робить повтор майже безкоштовним. Це дає відтворюваність і ефективність повторних запитів, які прямо згадані в завданні.»
- **Як перевірю:** евал «повторний ідентичний запит» — 0 HTTP-запитів і ті самі числа; евал «а тепер за 3 роки» — є `parent_run_id` і `resolve` не викликається.

## D7. Звіт, графік і захист від вигаданих чисел
- **Статус:** decided
- **Рішення:**
  - **Графік:** власний малювальник (~200 рядків) → SVG і прямо в PDF. На ньому частка по місяцях (індекс, перші 12 міс. = 100), тонка лінія зі сплесками й сіра зона «перекласифікація ботів 2025».
    - Змінено з `gonum/plot`: він тягне ~10 залежностей, серед них архівний `go-pdf/fpdf`. Тепер єдина залежність навички — `gopdf`.
  - **PDF:** `signintech/gopdf` з вбудованим шрифтом Noto Sans. Він покриває кирилицю, польські й чеські літери.
  - **Макет:** фіксований, на одну сторінку. Тест перевіряє, що сторінка рівно одна; задовгий текст обрізається з попередженням.
  - **Структура звіту:**
    1. заголовок-відповідь;
    2. 3 ключові числа;
    3. графік;
    4. таблиця мов із довірою;
    5. причини довіри;
    6. що перевірити далі;
    7. дрібним шрифтом — припущення, обмеження, «інтерес ≠ готовність платити».
  - **Числа.** Модель пише текст лише з плейсхолдерами (`{{uk.share_yoy_pct}}`), числа підставляє код. Якщо в тексті моделі є цифра поза плейсхолдером, `report` відхиляє текст із помилкою `RAW_NUMBER`.
- **Чому:** дешева модель може помилитися в числі або вигадати його. Плейсхолдери роблять це фізично неможливим. Вбудований шрифт гарантує, що кирилиця й діакритика відображаються на будь-якій ОС.
- **Відкинуті альтернативи:**
  - `go-pdf/fpdf`, `jung-kurt/gofpdf`, `wcharczuk/go-chart` — архівні бібліотеки без підтримки.
  - `maroto` — побудована на архівному gofpdf.
  - Валідатор, що лише звіряє числа, — слабший: модель може округлити або переставити цифри.
- **Як пояснити на захисті:** «Модель у мене не має права писати числа — лише посилатися на них. Кожне число у звіті походить з `result.json`, і це гарантує код, а не інструкція.»
- **Як перевірю:** тест PDF із текстом «Астрономія, Łódź, Příliš žluťoučký kůň» — ручна перевірка + перевірка кількості сторінок; тест валідатора: текст із «зросло на 12%» має бути відхилений.

## D8. Тестовий стенд
- **Статус:** decided
- **Рішення:**
  - **Основний стенд:** Claude Code з Haiku 4.5 у headless-режимі (`claude -p … --model haiku --output-format json`). 15 сценаріїв × 3 прогони.
  - **Другий стенд:** OpenCode + одна безкоштовна модель OpenRouter з надійним tool calling. Скорочений набір — 5 сценаріїв.
  - **Оцінювання:**
    - програмні перевірки: JSON, кількість сторінок PDF, числа тільки з `result.json`;
    - LLM-суддя за рубрикою (субагент `eval-judge`);
    - ручна перевірка 20% прогонів.
- **Чому:**
  - Відповіді моделі варіативні, один прогін нічого не доводить; три дають pass rate k/n.
  - Claude Code через OpenRouter гарантовано працює лише з моделями Anthropic, тому не-Anthropic модель ганяємо через OpenCode.
  - Друга модель доводить, що навичка не прив'язана до Claude.
- **Відкинуті альтернативи:**
  - Лише Haiku — не доводить переносимість.
  - Claude Code + OpenRouter free — ненадійно за документацією OpenRouter.
  - Свій агентний цикл — зайва робота для v1.
- **Як пояснити на захисті:** «Я тестую навичку як продукт: фіксований набір сценаріїв, кілька прогонів, автоматичні перевірки і суддя за рубрикою. Метрики — успішність, кількість викликів, токени, час.»
- **Як перевірю:** `make eval-full` → таблиця pass rate по сценаріях; ціль ≥13/15 сценаріїв проходять у всіх 3 прогонах.

## D9. Зовнішні сервіси (PostgreSQL, Redis, NATS, Qdrant)
- **Статус:** decided
- **Рішення:** у v1 жодних зовнішніх сервісів. Вони з'являються лише в roadmap.
- **Чому:** завдання вимагає самостійну навичку, яку агент запускає однією командою. Будь-яка база чи черга ламає це й ускладнює запуск у користувача.
- **Де доречні:**
  - v3 — Qdrant для семантичного групування тем через ембедінги;
  - v4 — окремий сервіс моніторингу для команди: PostgreSQL для історії, Redis для кешу й лімітів, NATS для черги збору даних.
- **Як пояснити на захисті:** «Я знаю цей стек, але свідомо його не використав: для однокористувацької навички це оверінжиніринг. Показую, в якій точці росту він стає виправданим.»
