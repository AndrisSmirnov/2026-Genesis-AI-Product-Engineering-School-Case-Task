# Wikipedia-навичка: ключові моменти та Research-промпт

Sep 27, 2026 · @Andris

## Ключові моменти задачі

Здати треба не аналіз, а інструмент: навичку, з якою дешева модель сама відповідає на запити про інтерес до тем і мов — з числами, рівнем довіри й обмеженнями.

### Жорсткі вимоги

| Вимога | Що це означає на практиці |
| --- | --- |
| Формат [Agent Skills](https://agentskills.io/specification) | `SKILL.md` з `name` (≤ 64 символи: a-z, 0-9, дефіс; збігається з назвою директорії) і `description` (≤ 1024 символи: що робить і коли застосовувати). Тіло бажано ≤ 500 рядків, решта — у `scripts/`, `references/`, `assets/`. Перевірка: `skills-ref validate`. |
| Власний код робить змістовну роботу | Завантаження, кеш, метрики, рівень довіри, графіки, PDF — у коді. Агент лише обирає команду й формулює висновок. |
| Відтворюване середовище, без бінарників | Lock-файл залежностей і одна команда запуску. Вимоги до середовища — у полі `compatibility`: Python, uv, мережа до wikimedia.org і wikidata.org. |
| Усе в директорії навички | Код, тести, евали, шаблон звіту, шрифти, документація, приклади звітів. |
| Зручно для швидкої дешевої моделі | Повний сценарій прогнаний на Haiku 4.5 або безкоштовній моделі OpenRouter; логи прогонів — доказ. |
| Графіки й короткий звіт | Наприклад, PDF на одну сторінку, яким можна поділитися. |
| План розвитку | Як ітеративно дійти до складніших досліджень і більших обсягів даних. |
| AI у розробці | Уміти пояснити, як ти перевіряв результат AI-інструментів. |

### Неявні вимоги: що, найімовірніше, оцінюють

- **Тема ≠ одна стаття.** Треба знайти відповідники в різних мовних розділах (наприклад, через Wikidata) і показати, які саме статті взято.
- **«Наскільки можна довіряти» — окремий вихід.** Потрібен рівень довіри з причинами, а не лише відсоток зростання.
- **Уточнення після першої відповіді.** Аналіз задається спекою, яку можна змінити й перезапустити; кеш робить повторні запити швидкими.
- **Порівнюваність мов.** Абсолютні перегляди польської та чеської Вікіпедії напряму не порівнюються — потрібна нормалізація.
- **Висновки з даних.** Кожне число у відповіді походить із виходу скрипта; припущення й обмеження — явно у звіті.
- **Інтерес ≠ готовність платити.** Звіт має це казати й радити, що перевірити далі.

### Пастки даних Wikipedia — гіпотези для перевірки в Research

- Редиректи рахуються окремо від цільової статті, а перейменування розриває історію переглядів.
- Частина ботів проходить як звичайні читачі й дає фальшиві піки; зміни класифікації ботів можуть розривати ряд.
- Разові сплески (новини, головна сторінка, Google Doodle) імітують зростання.
- Сезонність: тижнева й річна (інтервальне голодування — січень, астрономія — затемнення).
- Ефект платформи: загальний трафік Вікіпедії змінюється, а окремі розділи ростуть самі по собі — наприклад, україномовний після 2022.
- Мова ≠ країна: читачі однієї країни користуються кількома мовними розділами.
- Малі обсяги — шум і низька довіра.
- Технічне: обов’язковий User-Agent, ліміти запитів; per-article дані — орієнтовно з липня 2015.
- PDF із кирилицею та польськими й чеськими діакритиками потребує вбудованого шрифту.

## Що це означає для відеозахисту

Захист перевіряє твоє мислення без AI, тож флоу має залишати рішення за тобою, а агентам — виконання.

- **Формат:** 4 питання, до 5 хвилин на кожне разом із роздумами, наживо, українською, одна спроба без повернення.
- **Ймовірні теми** (прогноз із формулювань завдання, не реальні питання): архітектура й ключові рішення; як навичка оцінює довіру й перевіряє висновки; як ти тестував на дешевій моделі й перевіряв роботу AI; як розвивати навичку далі.
- **Два журнали на весь проєкт:** `DECISIONS.md` — рішення, альтернативи, чому; `VERIFICATION.md` — що згенерував AI і як ти це перевірив. Пишеш їх своїми словами.
- **Каркас відповіді:** контекст → рішення → альтернативи → як перевірив → обмеження → що далі.

## Рішення, які треба прийняти

Дев’ять рішень задають архітектуру; рекомендації нижче — гіпотези, які Research має підтвердити або спростувати.

| Рішення | Попередня рекомендація | Чому |
| --- | --- | --- |
| Мова коду | Python + uv (`pyproject.toml` + `uv.lock`) | Найсильніша екосистема для статистики, графіків і PDF; `uv run` відтворює середовище без бінарників. Go — для харнеса евалів або сервісу на етапі масштабування. |
| Інтерфейс для агента | CLI з 3–5 високорівневими командами: компактний JSON у stdout, великі дані — у файли | Дешева модель погано рахує й губиться в довгому контексті: код рахує, модель пояснює. |
| Тема → статті | Wikidata: сутність → sitelinks потрібних мов + редиректи; «кошик» статей — опційно, з підтвердженням | Однаково для будь-якої мови; неоднозначність повертається агенту як вибір для користувача. |
| Метрика інтересу | Частка теми від усіх переглядів мовного розділу + YoY і середньорічний темп | Прибирає ефект платформи й різний розмір розділів; абсолютні числа — довідково. |
| Довіра до тренду | Рівень високий / середній / низький із переліком причин | Кілька незалежних перевірок: значущість тренду, внесок сплесків, обсяг, узгодженість desktop і mobile, стійкість до зміни вікна. |
| Повторні запити | Спека аналізу (JSON або YAML) + локальний кеш (SQLite або DuckDB/Parquet) | Уточнення = змінена спека й перезапуск, дані вже в кеші. |
| Звіт | PDF на одну сторінку за шаблоном із вбудованим шрифтом; модель пише лише короткий текст | Скрипт звіряє числа в тексті з результатами — захист від вигаданих чисел. |
| Тестовий стенд | Claude Code з Haiku 4.5 у headless-режимі + одна модель через OpenRouter | Дві різні слабкі моделі: навичка не прив’язана до однієї. |
| Твій стек (PostgreSQL, Redis, NATS, Qdrant) | У базовій навичці — ні | Зовнішні сервіси зламають портативність. Доречні в roadmap: збирач на Go, черга NATS, Qdrant для семантичного групування тем. |

Праворуч — твої контрольні точки: без них агентний конвеєр видасть код, який ти не зможеш захистити.

**Компоненти Claude Code і середовище** (деталі уточнить Research, блок C):

- `CLAUDE.md` — правила проєкту: команди тестів, стиль, «контракт CLI не змінюється без оновлення евалів», записи в `DECISIONS.md`.
- Субагенти — рев’юер коду, рев’юер статистичної методики, тестувальник навички на Haiku: субагенту можна задати модель і підвантажити навичку.
- Хуки — лінтер і форматування після змін, тести перед завершенням кроку.
- skill-creator — евали й оптимізація `description`; `claude plugin eval` (early access) порівнює результат із базовою лінією без плагіна, тож навичку можна обгорнути в плагін.
- Headless-режим і `/goal` — автоматичний прогін евалів, доки не виконано умову.
- Середовище: розробляєш на Windows, тому фінальна перевірка — у чистому Linux-контейнері в Docker.

## Research-промпт для Claude Opus 5.5

Скопіюй блок цілком у новий Research-чат: текст завдання вже всередині, додавати нічого не треба.

```text
# Роль і мета
Ти — дослідник і архітектор агентних AI-систем. Проведи глибоке дослідження з веб-джерелами й підготуй звіт-основу для двох цілей:
1) спроєктувати й реалізувати навичку (Agent Skill) для аналізу переглядів Wikipedia, яка надійно працює на дешевій швидкій моделі (Claude Haiku 4.5 або безкоштовні моделі OpenRouter);
2) побудувати максимально автоматизований, але контрольований мною процес розробки в Claude Code (skills, субагенти, хуки, евали).

# Контекст
- Я backend-розробник: Go (4 роки), Python — друга мова. Мій стек: PostgreSQL, Redis, NATS, Qdrant. Розробляю на Windows (Git Bash, Docker Desktop на WSL2).
- Це кейс відбору на програму з AI-агентів. Повний текст завдання — наприкінці промпту; він має пріоритет над моїм викладом.
- Після здачі — усний захист без AI. Тому мені потрібні не лише рекомендації, а й обґрунтування: чому саме так, які альтернативи й компроміси.
- Сьогодні вересень 2026 року. Перевіряй актуальність усього, що могло змінитися після 2025 року.
- Не став уточнювальних питань: якщо чогось бракує, зроби розумне припущення і явно його познач.

# Мої гіпотези (підтверди, зміни або спростуй — з аргументами)
H1. Код навички — Python + uv (pyproject.toml + uv.lock); CLI з 3–5 високорівневими командами; компактний JSON у stdout, великі дані — у файли.
H2. Тема → статті в різних мовах: Wikidata (пошук сутності → sitelinks) + редиректи; «кошик» статей — опційно, з підтвердженням користувача.
H3. Основна метрика — частка переглядів теми від усіх переглядів мовного розділу; зростання — YoY, середньорічний темп (CAGR) і робастний нахил.
H4. Довіра до тренду — рівень високий / середній / низький із причинами, на основі кількох незалежних перевірок.
H5. Повторні й пов’язані запити — через спеку аналізу (JSON/YAML) і локальний кеш (SQLite або DuckDB/Parquet).
H6. Звіт — PDF на одну сторінку за шаблоном; числа підставляє код, модель пише лише короткий текст, а валідатор звіряє числа в тексті з результатами.
H7. Тестування — Claude Code з Haiku 4.5 у headless-режимі + одна модель через OpenRouter.

# Питання дослідження
Пріоритети: P0 — обов’язково й глибоко; P1 — важливо; P2 — якщо лишиться ресурс. Основний бюджет — на P0.

## A. Дані й методологія
A1 (P0). Wikimedia Analytics API, page views: актуальні ендпоінти (per-article, aggregate, top, дані за країнами, unique devices), параметри (project, access, agent, granularity), з якої дати є дані, затримка оновлення, обмеження діапазонів, коди помилок, вимоги до User-Agent, ліміти запитів і зміни 2025–2026 років. Чи змінилися базові URL і документація порівняно з REST v1?
A2 (P0). Пастки даних і способи їх обробки: редиректи й перейменування статей; класифікація ботів (user / spider / automated) та її зміни; сплески від новин, головної сторінки, Google Doodle, соцмереж; зсув desktop → mobile; загальні зміни трафіку Wikipedia (зокрема через AI-відповіді в пошуку); зростання окремих розділів (наприклад, україномовного після 2022). Які інструменти й дослідження вже це розв’язують (Pageviews Analysis, наукові роботи)?
A3 (P0). Як надійно зіставити тему з набором статей у різних мовах: Wikidata (wbsearchentities, sitelinks), MediaWiki API (redirects, categories, links), неоднозначність, відсутні статті. Коли достатньо однієї статті, а коли потрібен «кошик»; як будувати кошик відтворювано.
A4 (P0). Методика «чи зростає інтерес і наскільки цьому довіряти»: нормалізація, YoY, CAGR, лог-лінійний тренд, Theil–Sen, Mann–Kendall (зокрема сезонний), STL, робастна обробка сплесків (Hampel / MAD), bootstrap-інтервали, мінімальні обсяги, аналіз чутливості (інші вікна, без сплесків). Як звести це в зрозумілий рівень довіри без хибної точності? Запропонуй конкретні критерії й пороги як гіпотези, які я перевірю на синтетичних рядах із відомою відповіддю.
A5 (P1). Мова ≠ ринок: як пов’язати мовні розділи з країнами й аудиторіями; які безкоштовні сигнали додати для перехресної перевірки; межі висновків («інтерес ≠ готовність платити»).

## B. Дизайн навички для дешевої моделі
B1 (P0). Специфікація Agent Skills (agentskills.io): поля frontmatter та обмеження, структура директорії, progressive disclosure, валідація (skills-ref). Які агенти й середовища підтримують стандарт зараз і чим відрізняється їхня поведінка (запуск скриптів, мережевий доступ, завантаження references).
B2 (P0). Best practices авторства навичок (документація Anthropic та інших): довжина й структура SKILL.md, як писати description для надійного спрацювання, workflow-чеклісти, скрипти vs інструкції, що змінюється, коли навичку виконує маленька модель.
B3 (P0). Дизайн CLI для слабкої моделі: кількість і гранулярність команд, схема JSON-виходу, бюджет токенів (не віддавати сирі ряди в контекст), помилки з підказкою наступного кроку, ідемпотентність, спека для уточнень, кеш, захист від вигаданих чисел.
B4 (P1). Технічний вибір: Python + uv vs Go vs TypeScript саме для цієї навички (відтворюваність, заборона бінарників, робота на Windows, macOS і Linux). Бібліотеки для HTTP, даних, статистики, графіків і PDF з актуальними версіями й ліцензіями. Як гарантувати PDF рівно на одну сторінку й коректну кирилицю та польські й чеські діакритики.
B5 (P1). Що має бути в односторінковому звіті для фаундера B2C-продукту; як показувати невизначеність, припущення й обмеження.

## C. Процес розробки й тестування
C1 (P0). Актуальні можливості Claude Code для цього проєкту: CLAUDE.md і rules, skills, субагенти (вибір моделі, підвантаження навичок), хуки, plan mode, headless-режим, /goal, workflows, плагіни, skill-creator, claude plugin eval (early access), /skill-doctor. Запропонуй конкретну структуру .claude/ для проєкту і послідовність етапів.
C2 (P0). Eval-driven розробка навички: 10–15 сценаріїв (зокрема уточнення після першої відповіді, неоднозначні теми, відсутні статті, малі обсяги, «фальшиве» зростання через сплеск), критерії успіху, оцінювання (програмні перевірки + LLM-суддя з рубрикою + ручна вибірка), метрики (успішність, виклики інструментів, токени, вартість, час), кількість повторів через варіативність.
C3 (P0). Стенд для дешевих моделей: які агентні CLI зараз підтримують Agent Skills разом з OpenRouter; чи можна запускати Claude Code через OpenRouter; коли простіше написати мінімальний власний агентний цикл; чи має сенс локальна модель (Ollama / llama.cpp) як додатковий безкоштовний стенд.
C4 (P1). OpenRouter free: актуальні ліміти, які безкоштовні моделі мають надійний tool calling, підводні камені (ліміти, логування даних, зникнення моделей).
C5 (P1). Як перевіряти код і аналітику, згенеровані AI: TDD, синтетичні ряди з відомою відповіддю, записані відповіді API як фікстури, property-based тести, крос-рев’ю іншою моделлю, журнали рішень і перевірок.
C6 (P1). Roadmap розвитку: складніші дослідження (багато тем і мов, власні критерії перспективності), великі обсяги (конкурентні запити з лімітами, DuckDB / Parquet, дампи замість API, інкрементальні оновлення), семантичне групування тем, моніторинг за розкладом; де доречний окремий сервіс на Go з PostgreSQL, Redis, NATS, Qdrant, а де це зайве.

1. Резюме: 10–12 ключових висновків і рекомендацій.
2. Вердикт по H1–H7: підтверджено / змінити / спростовано — і чому.
3. Таблиця рішень: рішення | варіанти | рекомендація | обґрунтування | ризики.
4. Детальні знахідки за блоками A, B, C.
5. Чернетки артефактів:
   - дерево директорії навички;
   - контракт CLI: команди, аргументи, приклад JSON-виходу;
   - методика рівня довіри: критерії, пороги-гіпотези, приклади формулювань для звіту;
   - 10–15 евал-сценаріїв із критеріями успіху;
   - структура .claude/ (CLAUDE.md, субагенти, хуки) і етапи розробки;
   - roadmap v1 → v4.
6. Топ-10 пасток і антипатернів.
7. Відкриті питання, які я маю вирішити сам.
Не пиши повну реалізацію — лише короткі фрагменти коду чи псевдокод, де це пояснює ідею.

# Вступ

Командам B2C-застосунків постійно доводиться вирішувати, у що інвестувати далі: додати новий курс у навчальний застосунок, охопити іншу тему чи локалізувати продукт ще однією мовою. Щоб обрати, куди вкладати час і гроші, потрібно розуміти, що цікавить потенційну аудиторію та як цей інтерес змінюється.

Одне з потенційних джерел такого розуміння — Wikipedia. Wikimedia публікує статистику переглядів статей різними мовами, за якою можна досліджувати, як змінюється інтерес до тем. Звісно, інтерес до статті ще не означає готовність платити за продукт, але точно може допомогти обрати напрям для подальшої перевірки.

У рамках цього завдання пропонуємо розробити навичку для AI-агента, використовуючи яку засновники B2C-продуктів зможуть вирішувати, які теми розвивати далі та якими мовами запускати свій продукт.

## Завдання

Результатом виконання цього завдання має бути самостійна навичка у форматі [Agent Skills](https://agentskills.io/specification), яка дозволить агенту аналізувати [дані про перегляди Wikipedia](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html), генерувати графіки та формувати короткі звіти, якими можна поділитися, наприклад PDF на одну сторінку.

Приклади запитів:

- Порівняй зростання інтересу до інтервального голодування в польськомовній та чеськомовній Wikipedia за останні два роки.
- Ми думаємо додати курс з астрономії до освітнього застосунку. Чи зростає інтерес до цієї теми в україномовній Wikipedia, і наскільки цьому зростанню можна довіряти?
- Ми створюємо застосунок для вивчення мов. Порівняй інтерес до вивчення англійської у вибраних нами мовних розділах та підготуй короткий звіт: які аудиторії варто дослідити наступними й чому?

Це лише приклади: користувачі матимуть власні теми, мови та критерії перспективності. Вони також можуть уточнювати запити й змінювати припущення після першої відповіді. Решту вирішуєш ти.

Продумай, як навичка допомагатиме агенту оцінювати результати, перевіряти висновки та ефективно виконувати повторні й пов’язані запити. Важливо, щоб рекомендації та звіти спиралися на дані, а їхні припущення й обмеження були зрозумілими.

Після того як навичка зможе відповідати на базові запити, поясни, як її ітеративно розвивати далі, щоб вона працювала зі складнішими дослідженнями та більшими обсягами даних.

## Вимоги

Обов’язкового стеку немає: можна використовувати Python, TypeScript, Go або іншу мову.

Навичка має містити `SKILL.md` та власний код, який виконує змістовну частину роботи з даними. Одного Markdown-файлу або інструкцій агенту щоразу самостійно написати потрібний код недостатньо. Не додавай скомпільовані виконувані файли; залежності та підготовка середовища мають бути відтворюваними. Усі власні матеріали й код мають бути в директорії навички.

Навичкою має бути зручно й ефективно користуватися агенту на швидкій недорогій моделі, наприклад Claude Haiku 4.5 або аналогічній із підтримкою інструментів. Навіть якщо користувачі обиратимуть найпотужніші моделі, це обмеження допоможе перевірити якість реалізації. Перевір повний сценарій на такій моделі; для цього можна скористатися недорогими або [безкоштовними моделями OpenRouter](https://openrouter.ai/docs/guides/routing/model-variants/free), враховуючи їхні можливості та ліміти.
```

## Як запустити й що робити з результатом

Запусти Research один раз із повним промптом; якщо якийсь блок вийде поверхневим — перезапусти A, B і C окремо.

2. Поверхневий звіт → три окремі запуски: у промпті залиш «Роль і мета», «Контекст», «Гіпотези», «Джерела», «Формат звіту», текст завдання й лише один блок питань.
